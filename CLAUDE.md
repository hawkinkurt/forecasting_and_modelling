# UK macro monitor

Monitoring tools, forecasting models and chart packs on the UK and US economies (plus other areas over time). General working preferences, environment and personal context live in the author's global `~/.claude/CLAUDE.md`, outside this repo; this file covers this project only.

## Environment

- Data work leans on SQL in DuckDB where it is natural.
- Database: DuckDB at `data/uk_monitor.duckdb` (gitignored, along with `exports/`).
- Power BI Desktop for dashboards. Power BI does not read DuckDB, so `export.py` writes Parquet files to `exports/` and Power BI reads those. After an ingest: run `export.py`, then Refresh in Power BI.

## Current state of the code

- `sql/schema.sql`: tables `series` (metadata), `observations` (vintage-aware: one row per series, period and vintage date), `fetch_log`, `forecasts` (keeps every forecast with date made and model, for later accuracy tracking).
- `sql/views.sql`: all derived measures, each with a comment explaining the economics and the SQL technique.
  - `latest_observations`, `latest_observations_labelled`: most recent vintage per period.
  - `analysis_series`: M and Q series as published, plus daily series as monthly averages (`is_complete` false for the current month).
  - `changes`: period, y/y and 3m-on-3m annualised changes. % for `level`, pp for `rate`, units for `balance`. Uses RANGE windows with calendar intervals so gaps give NULL rather than wrong comparisons.
  - `real_pay` (pay growth deflated by 3m avg CPIH), `yield_curve` (daily spreads in bp), `real_policy_rate` (Bank Rate minus CPI), `psnb_fiscal_year` (fiscal-year-to-date borrowing vs last year).
  - `heatmap`: each series' reading on its `heatmap_basis` (value, yoy for trending levels, sum12 for seasonal flows) and its PERCENT_RANK within its own last 10 years (percentile, not z-score, because 2020 outliers would compress z-scores). `reading_display` is scaled/rounded to match `series.heatmap_label`.
  - `revisions` (first vs latest estimate, `is_backfill` flags the initial load), `latest_snapshot` (one row per series for dashboard cards), `data_health` (ok / stale / overdue / error per series).
- Validated: derived GDP q/q matches the ONS published series exactly on all quarters. Derived retail sales y/y matches the published series to within 0.1pp (0.2pp once in the 2000s), the gap being rounding of the 1dp published index.
- `series.csv`: the registry, one row per tracked series (source, source code, dataset, name, short_name (used in charts, Power BI measure names and the email; keep stable, renaming changes measure names), section, frequency D/M/Q/A, units, measure rate/level/balance, optional multiplier e.g. -1 to flip a sign convention). Source of truth, synced into the `series` table each run.
- `run.py`: the whole pipeline. Sync registry, fetch each series (one transaction per series, errors logged and skipped), store, update `last_fetched`/`next_release`, print the "what changed" report, export Parquet, then build and send the email report (every run; `--no-email` skips sending). Run manually for now.
- `pipeline/email_report.py`: the "what changed" email, sections in this order (the author's choice): 0. At a glance heatmap (last 6 months per series, coloured by percentile in a colour-blind-safe blue-to-orange scale that signals "unusual", not good/bad; compact table attributes because Gmail clips HTML over ~100KB, currently ~80KB, so check size when adding content); 1. New releases (M/Q series with a new period this run: latest, previous, consensus and surprise = actual minus consensus on the same basis, change vs a year ago, 5-year sparkline, release time); 2. Coming up (each release in the next 7 days with its exact time and any consensus captured since the series was last published), then "Consensus captured" listing new rows for checking; 3. Markets (every daily series, always shown, with 1-day and 1-month changes); 4. All UK data (every M/Q series, grouped by section, NEW badge on those updated this run), so the email is a complete picture every day; 5. Revisions (only recent periods listed, older seasonal-adjustment revisions counted); 6. Problems (fetch errors and `data_health`). New vs revised is found by comparing rows with `fetched_at >= run start` against the previous vintage. Sent via the Gmail API (`pipeline/gmail.py`, HTTPS) because the author's network blocks SMTP ports 465 and 587. OAuth scope is `gmail.send` only. OAuth client `config/gmail_credentials.json` and token `config/gmail_token.json` are gitignored; one-off consent with `python -m pipeline.gmail` (opens a browser, run it in the user's terminal). Daily runs never open a browser and report a clear message if re-authorisation is needed. Sender and recipient come from `GMAIL_ADDRESS` and `REPORT_TO` in `.env`. send_report never raises, so mail problems cannot break a data run. Always saves `exports/last_report.html`. Change colours are deliberately neutral (a rise is not always good news). Inline images use cid references. Sparklines cover 3 years (1 year for daily) and draw the previous release (latest value per period from vintages before the series' latest vintage) as a red dotted line under the blue latest line, plus a red REVISED tag when they differ; empty until a series has two vintages. Series names link to the latest ONS release page (`series.last_release_url`, from the release calendar); each row ends with a News button (Google News, past 7 days, phrase from `news_query` in series.csv).
- `pipeline/calendar.py`: exact last/next release times from the ONS release calendar (`/v1/search/releases`, `sort=release_date_desc|asc`, `release-type=type-published|type-upcoming`). Titles are "<ons_release>: <period>"; "time series" companion entries are excluded. Stored as London time in `series.last_release_at` / `next_release_at`. `ons_release` in series.csv names the release(s), "|"-separated (quarterly GDP is in both the first estimate and the quarterly national accounts).
- Consensus: `consensus_inbox/consensus.csv` (gitignored: Bloomberg's data, personal use) holds series_id, period, basis (value/mom/qoq/yoy), consensus, as_of, event_as_shown, source. `pipeline/consensus.py` validates rows against the registry and loads them into the `consensus` table each run. Rows are added by the **`/consensus` project skill** (`.claude/skills/consensus/SKILL.md`), which reads Bloomberg calendar screenshots inside Claude Code, or typed by hand. **No paid Anthropic API**: the author does not want to rely on one. Never automate fetching Bloomberg's site (terms of use and bot protection).
- `pipeline/`: `db.py` (connection, `ensure_schema`), `registry.py` (load/validate/upsert), `store.py` (vintage logic), `report.py`, `sources/` (one fetcher per source returning `FetchResult(rows, vintage_date, next_release)`, registered in `sources/__init__.py`).
- `pipeline/sources/ons.py`: ONS beta API. Resolves the full URI from CDID + dataset via the search endpoint each run. Release timestamps are converted to London time (BST midnight arrives as 23:00 UTC the day before).
- `pipeline/sources/boe.py`: Bank of England IADB CSV download, one request per series, `dataset` = `IADB`. No release dates, so vintage = date fetched (London time). Monthly data are dated at month end by the BoE and moved to the first of the month. Start date must be 01/Jan/1963 or later. Bad requests return an HTML page with status 200, so the fetcher checks the content type.
- All fetchers send the honest `USER_AGENT` from `sources/base.py`. The BoE blocks Python's anonymous default user agent. Never disguise requests as a browser.
- `setup_db.py`: creates the tables and views on its own. Safe to re-run.
- `export.py`: writes Parquet files to `exports/` for Power BI.
- `powerbi/`: the dashboard as a Power BI Project (`UK Macro Monitor.pbip`, PBIR report + TMDL model). **Generated by `powerbi/build_pbip.py`**, which owns `model.tmdl`, `expressions.tmdl`, `relationships.tmdl`, `tables/` and the report pages. Make dashboard changes in the script, then regenerate. Power BI Desktop must be closed when regenerating, and should be closed with "Don't save" after viewing so it does not rewrite the files. IDs are uuid5 from object names, so regeneration is deterministic.
  - Model: star schema. `Series` and `Date` (calculated, marked as date table) filter the fact tables. Parameters `ExportFolder` and `DashboardStart` (2000-01-01). Auto date/time is off.
  - Measures: `Series Value`, `Latest Value`, one measure per series (short names in `SHORT_NAMES`) plus `Latest: ...`, and specific measures on Changes, RealPay, YieldCurve, RealPolicyRate, PsnbFiscalYear.
  - Pages: Overview (cards + heatmap matrix: `pivotTable` with Rows/Columns/Values, cell colours by field value from the `Heatmap colour` / `Heatmap text colour` measures), Latest data, Activity, Labour market, Inflation, Rates and money, Public finances and external, Data health.
  - Series rows sort by `display_order` (series.csv order) via sortByColumn on `short_name` and `heatmap_label`.
  - Lessons: DAX variable names must not clash with DAX functions (e.g. `LastDate`). Measure names must not match a column name on the same table (case-insensitive). Visual roles used: lineChart/clusteredColumnChart `Category`/`Y`, card `Values`, tableEx `Values`, slicer `Values`. Format literals: strings in single quotes, e.g. `'Between'`. visualContainer schema 2.13.0 works with Desktop 2.159 (Oct 2026).
  - Verify changes by opening the .pbip in Desktop, pressing Refresh and checking each page.
- `scratch.py`: personal exploration, gitignored.

Conventions to keep: periods stored as the first day of the month, quarter or year, real-time vintages preserved (never overwrite history), series identified by a short `series_id`. Store what the source publishes (levels, or the official headline rate where that is the headline, e.g. CPI y/y and the unemployment rate) and derive everything else in SQL views. Pick the ONS dataset that is updated at every release of a series (e.g. `pn2` for quarterly GDP).

Known data notes: LFS series are labelled by the last month of the rolling 3 months. ONS `J5II` (PSNB) is published with negative = borrowing, flipped with multiplier -1. Payrolled employees (PAYE RTI) are not in the ONS time-series API and need an Excel-based fetcher. The IADB has no 2-year gilt par yield (daily par yields are 5, 10 and 20 years). A 2-year rate would need the BoE yield curve files.
